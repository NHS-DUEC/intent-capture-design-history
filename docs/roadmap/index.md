This roadmap describes the next documentation work needed to turn the design history into a more complete record of the AI Intent Capture programme.

It is a documentation roadmap, not a delivery roadmap. It records what the design history needs next so the repository remains useful for onboarding, challenge, governance and future decision-making.

## Recently completed

These foundations are now in place:

- the homepage explains the purpose of the design history
- user needs have introductory context
- initial decision records have been added
- core concepts have working definitions
- an initial evidence page exists
- the evolution from AI Navigation to Intent Capture has been documented

## Now

Focus on making the design history more traceable and easier to challenge.

- Add a programme timeline from May 2026 onwards.
- Add a glossary and terminology history.
- Improve the evidence index so claims point to supporting artefacts.
- Add an assumptions register.
- Add an architecture page showing how Intent Capture relates to navigation, orchestration and onward services.

## Next

Focus on making the design history more useful for product, clinical safety and technical discussions.

- Add a post explaining the relationship between Intent Capture, Intelligent Navigation and Unified Access.
- Add decision records for non-AI routes, safe handover, emergency presentations and structured intent.
- Add a research backlog organised by assumption, risk and evidence gap.
- Add a meeting and artefact index.
- Add diagrams for ecosystem relationships and service boundaries.

## Later

Focus on maintainability and contribution.

- Add contributor guidance.
- Add a release note pattern for major updates.
- Decide whether assumptions, risks, glossary terms and evidence entries should be managed through Decap CMS.
- Review whether the top-level navigation still reflects the most useful reader journeys.
- Add guidance on how to archive or supersede old design positions without rewriting history.

## Open questions

- What should be treated as an agreed decision rather than an emerging design position?
- Which artefacts should be referenced publicly and which should remain internal?
- How much programme context should sit in the design history versus other team documentation?
- Should the repository include Architecture Decision Records, Design Decision Records, or a combined format?
- What evidence is needed before proposed decision records can be marked as accepted?
